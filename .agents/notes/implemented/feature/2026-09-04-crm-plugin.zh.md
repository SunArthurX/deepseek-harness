# Agent Note: 面向投资顾问的企业级 CRM 插件

Status: implemented

[English](2026-09-04-crm-plugin.md) | 中文

## Problem

Harness 此前没有客户关系管理能力：使用 `dsh` 的顾问团队（投资顾问/财富管理）可以保留会话日志，但该领域的持久业务对象——带风险测评的客户档案、顾问名册、互动历史、适当性审计咨询、商机管线、跟进任务——没有归宿。代理为客户做的任何事都随会话消亡，而顾问工作中合规关键的部分（中国证券业适当性：客户容忍度 C1–C5 对应产品风险 R1–R5、测评有效期、完整审计轨迹）完全没有强制点。

## Decision

三个包在新 `packages/crm/` 组下构成 CRM 能力缝：

- `packages/crm/crm`（`@deepseek-ai/dsh-crm`，服务 `ctx.crm`，注入 `storageDomain`，必填配置 `riskProfileValidityDays`）拥有一个含七张 Zod 校验表的持久 `crm` 存储域——顾问、方案、客户、互动、咨询、商机、任务——以及业务规则：纯适当性引擎、商机阶段状态机（won/lost/abandoned 为终态；lost/abandoned 需要收尾原因；进入终态盖章收尾时间并强制概率）、顾问解析、写入时引用完整性，以及读模型分析（管线、客户簿、任务负载、适当性审计）。所有变更在一条服务级链上串行。
- `packages/crm/tool-crm`（`@deepseek-ai/dsh-tool-crm`，插件 `tool-crm`，注入 `tools`+`crm`）注册 22 个面向模型的 `crm_*` 工具（含投顾方案族 `crm_plan_create`/`list`/`review`/`transition`）。工具层只负责线上转换——ISO 8601 时间戳、封闭枚举词汇、规范记录序列化——在与纯序列化器保持同步的 `additionalProperties: false` 模式之下。

承重决策：

- **跨会话旁路域，而非会话事件。** CRM 记录必须比任何对话长寿且绝不隐式进入模型历史；域存储（与 `message-feedback` 和 `workspace` 一致）是事实来源。不新增 `SessionEventMap` 成员，持久化目录因此不动。工具结果已由工具管线记录，"模型可见即可重建"依然成立。
- **存储缝即提供者缝。** 服务只注入 `storageDomain`；SQLite/JSON 后端是部署路由。CRM 专属的 Definition/Provider 包拆分会重复存储栈已提供的那条缝。
- **适当性被评估并存储，绝不作为写入屏障强制。** `recordConsultation` 记录每个讨论产品及其判定与依据，即使判定不利——审计轨迹必须完整；模型呈现被阻断的判定而非推荐。这映射真实合规：记录"不匹配发生了"正是要点。
- **逾期是派生的，绝不落盘。** 是否逾期在读取时按调用方时钟计算；落盘的标记会过期。同一原则使 `profileStatus`（valid/expiring/expired/missing，固定 30 天预警窗口）只出现在读模型上。
- **凡可泄漏处皆确定性。** 文本排序使用 UTF-16 码元而非 `localeCompare`（与 ICU 构建无关），种子数据来自固定种子的 LCG，测试断言从种子自身记录重算分析期望而非手抄数字。
- **真实的不变式伴随插件。** `crm` 包的伴随插件在 `domain/changed` 上断言落库行的跨表引用完整性（与服务在每次变更内强制的规则相同）；工具包的伴随插件为空并说明理由。

## Alternatives considered

- **合并服务与工具的单包** — 否决：能力缝规则；服务（数据+规则，供产品表面消费）与工具（模型词汇）独立演进，且 `workspace`/`message-feedback` 为域支撑服务树立了先例。
- **带独立 CRM Definition/Provider 拆分的三包** — 否决：CRM 数据的可替换提供者层就是存储后端缝；CRM 内部的提供者拆分将是缝上之缝且只有一个实现。
- **用会话事件承载 CRM 状态** — 否决：客户档案必须先于并长寿于会话；放在每会话日志上会按对话分叉记录并违背会话事件"持久事实在重载后存活"的意图。
- **专门的 `crm_*` 删除 API** — 否决：审计姿态保留每一行；退役即 `lifecycle: lost` / `stage: abandoned` / `status: cancelled`。硬删除会摧毁咨询审计轨迹的引用完整性。
- **全可空的线上字段** — 曾考虑用以减少模式分支；否决，改为可选键模式加条件包含，符合仓库的序列化器习惯（message-feedback）并让缺失字段可见地缺失。

## Consequences

- 仓库获得第一个业务领域能力组（`packages/crm/`）；组 README 与生成的工具/配置目录承载它，未来业务领域包有了结构模板。
- 顾问组装必须显式配置 `riskProfileValidityDays`——没有默认窗口，运营者无法静默继承一个合规相关的期限。
- 22 个 `crm_*` 工具为挂载它们的 profile 增加固定模式成本；PTC 模式免费获得可调用的 `tools.crm_*` 函数与类型化返回。
- CRM 存储随部署的存储后端路由，已组装 `storage-sqlite` 的 profile 无需为 CRM 域增加额外后端配置。
- 未新增任何 `SessionEventMap` 成员，较旧的构建读取带 CRM 部署写出的日志无需任何词汇变更。

## Iteration log

- 门槛轮次（4）：按导出形态的 constraints files 清单、knip 未用依赖/导出、hygiene。
- 第 49 轮——以 CI 原始形态执行覆盖率门槛（`pnpm run test:coverage`，五次完整运行）：在 CRM 包之外发现并修复三个真实缺陷。其一，宿主 PATH 中自装的 git 2.23 排在 Apple 2.39 之前；把 /usr/bin 提前使三套 git 绑定的 spec 直接转绿。其二，spill-local 边界测试是真实 flake（文件系统 mtime 舍入使名义边界文件以约 40% 概率变为严格更早）；现在把截止时间钉在存盘后向下取整的 mtime 上——6/6 稳定。其三，上一任务未提交的 session-import 以 99.09% 分支未达 per-file 门槛：zcode 无 query 的列表路径无测试、复合 `&&` 条件触发 v8 计数伪影；补无 query 列表测试并做语义不变的条件重塑后清零。修复后每次运行均为零 per-file 阈值违规；每次完整运行剩余的一两个失败是轮换出现的 fs-watch 负载 flake（app-boot hmr-config/user-patches、experimental inspector），每个都在隔离重试与干净 HEAD 上通过——该信号由 CI 负责。
