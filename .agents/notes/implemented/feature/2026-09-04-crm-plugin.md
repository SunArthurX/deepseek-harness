# Agent Note: Enterprise CRM plugin for investment advisory

Status: implemented

English | [中文](2026-09-04-crm-plugin.zh.md)

## Problem

The harness had no Customer Relationship Management capability: an advisory team (投资顾问/财富管理) using `dsh` could keep session logs, but the durable business objects of the domain — clients with risk assessments, the advisor roster, engagement history, suitability-audited consultations, the opportunity pipeline, follow-up tasks — had no home. Anything the agent did for a client died with the session, and the compliance-critical parts of advisory work (Chinese securities suitability: client tolerance C1–C5 against product risk R1–R5, assessment validity windows, complete audit trails) had no enforcement point at all.

## Decision

Two new packages form the CRM capability seam under the new `packages/crm/` group:

- `packages/crm/crm` (`@deepseek-ai/dsh-crm`, service `ctx.crm`, inject `storageDomain`, required config `riskProfileValidityDays`) owns one durable `crm` storage domain with six zod-validated tables — advisors, clients, interactions, consultations, opportunities, tasks — plus the business rules: the pure suitability engine, the pipeline stage machine (won/lost/abandoned terminal; lost/abandoned require a close reason; terminal entry stamps close time and forces probability), advisor resolution, write-time referential integrity, and read-model analytics (pipeline, book, task load, suitability audit). All mutations serialize on one service-level chain.
- `packages/crm/tool-crm` (`@deepseek-ai/dsh-tool-crm`, plugin `tool-crm`, inject `tools`+`crm`) registers 18 model-facing `crm_*` tools. The tool layer owns wire conversion only — ISO 8601 timestamps, closed enum vocabularies, canonical record serialization — under `additionalProperties: false` schemas kept in lockstep with pure serializers.

Load-bearing choices:

- **Cross-session sidecar domain, not session events.** CRM records must outlive any conversation and never enter model history implicitly; the domain store (like `message-feedback` and `workspace`) is the source of truth. No new `SessionEventMap` members, so the persistence catalog is untouched. Tool results are already logged by the tool pipeline, which keeps "model-visible means logged" true.
- **The storage seam is the provider seam.** The service injects only `storageDomain`; SQLite/JSON backends are deployment routing. A CRM-specific Definition/Provider package split would have duplicated the seam the storage stack already provides.
- **Suitability is evaluated and stored, never enforced as a write barrier.** `recordConsultation` records every discussed product with its verdict and rationale even when the verdict is unfavorable — the audit trail must be complete; the model surfaces blocked verdicts instead of recommending. This mirrors how real compliance works: recording that a mismatch happened is the point.
- **Overdue is derived, never stored.** A task past due is computed on read against the caller's clock; a stored flag would go stale. The same principle puts `profileStatus` (valid/expiring/expired/missing, fixed 30-day warning window) on read models only.
- **Determinism everywhere it can leak.** Text ordering uses UTF-16 code units rather than `localeCompare` (ICU-build independent), seed data derives from a fixed-seed LCG, and test assertions recompute analytics expectations from the seed's own records rather than hand-copied numbers.
- **A real invariant companion.** The `crm` package's companion asserts cross-table referential integrity of landed rows on `domain/changed` (the same rules the service enforces inside each mutation); the tool package's companion is empty with a stated reason.

## Alternatives considered

- **One package combining service and tools** — rejected: the capability-seam rule; the service (data + rules, consumed by product surfaces) and the tools (model vocabulary) evolve independently, and `workspace`/`message-feedback` set the precedent for domain-backed services.
- **Three packages with a separate CRM Definition/Provider split** — rejected: the swappable provider layer for CRM data is the storage backend seam; a CRM-internal provider split would be a seam over a seam with one implementation.
- **Session events for CRM state** — rejected: client records must predate and outlive sessions; putting them on the per-session log would fork the record per conversation and violate the "durable facts survive reload" intent of session events.
- **A dedicated `crm_*` delete API** — rejected: the audit posture keeps every row; retirement is `lifecycle: lost` / `stage: abandoned` / `status: cancelled`. Hard deletes would gut the consultation audit trail's referential integrity.
- **Nullable-everything wire fields** — considered to reduce schema branches; rejected in favor of optional-key schemas with conditional inclusion, matching the repo's serializer idiom (message-feedback) and keeping absent fields visibly absent.

## Consequences

- The repo gains its first business-domain capability group (`packages/crm/`); the group README and the generated tool/config catalogs carry it, and future business-domain packages have a structural template.
- Advisory compositions must configure `riskProfileValidityDays` explicitly — there is no default window, so an operator cannot silently inherit a compliance-relevant lifetime.
- The 18 `crm_*` tools add fixed schema cost to any profile that mounts them; PTC mode gets them as callable `tools.crm_*` functions with typed returns for free.
- CRM storage rides the deployment's storage backend routing, so a profile that already composes `storage-sqlite` needs no extra backend config for the CRM domain.
- No `SessionEventMap` members were added, so older builds read logs written by CRM-carrying deployments without any vocabulary change.
